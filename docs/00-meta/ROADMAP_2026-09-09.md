## Fase 1 — Correção estrutural da apresentação

### 1.1 Adjacência cross-region — CONCLUÍDO

O compositor cobre vizinhança cardinal e diagonal entre regiões modulares.

Gates concluídos:

- contactos cardinais;
- contactos diagonais corner-only;
- reciprocidade das máscaras;
- tolerância de ponto flutuante;
- separação além da tolerância;
- fail-closed de contactos inválidos;
- aplicação idempotente;
- testes sobre todas as quatro orientações diagonais.

Evidência: PR #247 + PR #248.

### 1.2 Swapchain recreation fail-closed — CONCLUÍDO

`Swapchain::recreate()` passou a preservar a geração atualmente válida até a geração de substituição ter sido criada e todos os image views terem sido construídos com sucesso.

Gates concluídos:

- recursos anteriores permanecem vivos durante a tentativa de substituição;
- `oldSwapchain` é passado à nova criação;
- publicação do estado novo só ocorre depois de criação completa;
- recursos antigos só são destruídos depois da publicação;
- falha não deixa o owner com handles já destruídos pela própria recreation;
- cobertura de lifecycle/preconditions em testes.

Limitação conhecida: ainda não existe uma seam de injeção de falha Vulkan determinística para provar cada erro de criação de recurso individual. Essa é uma melhoria separada de testability, não uma razão para reabrir a correção transacional.

Evidência: PR #250, merge `bae8ccdc2c4abd8da3c675893c7063731ba830b3`.

### 1.3 Camera bounds + subpixel stability — PRÓXIMO

Usar o benchmark existente `movement_camera_benchmark.py` como oracle numérica e alinhar os testes C++ com:

- limites inferiores;
- viewport válido/inválido;
- grandes `dt` sem overshoot;
- tracking monotónico;
- estabilidade de conversão world→NDC;
- comportamento preparado para subpixel jitter sem introduzir drift acumulativo.

Não alterar física para resolver problemas de camera.

### 1.4 Mapas `NaoValidados` — DEPOIS DE 1.3

Executar validação dirigida dos mapas marcados `NaoValidados`, separando claramente:

```text
validade estrutural
vs.
playability/physics
vs.
captura/visual
```

Não transformar falhas de conteúdo em relaxamento das regras do validator.

Só iniciar com baseline funcional estável.

### 2.2 Vertex/GPU batching

## Assets — estado e ordem

A promoção de assets continua bloqueada quando não existe o binário exato verificável.

Regras:

- preview/nome/licença não equivalem a ficheiro runtime;
- `CC0` não equivale a aprovação;
- dimensões devem ser verificadas no ficheiro concreto;
- hashes e runtime paths só são registados quando o ficheiro existe;
- qualquer candidato `REWORK` permanece fora do runtime.

## CI / engenharia

### Artifact finalization 403 — RESOLVIDO COMO INCIDENTE OPERACIONAL

O caso de 2026-09-09 foi reproduzido e resolvido por rerun do mesmo job sem alterações de código/permissões.

Política:

```text
FinalizeArtifact 403 depois de upload bem-sucedido
→ rerun do job falhado
→ confirmar artifact finalizado
→ só alterar configuração se o padrão se repetir com evidência
```

Não adicionar `actions: write` apenas para este erro.
Não usar `retry-max-attempts` no `upload-artifact`, pois não é input suportado.

### Actions — MODERNIZADAS

Linux workflows usam `actions/checkout@v6`; deterministic capture usa `actions/upload-artifact@v6`, alinhando-se com o Windows workflow e removendo a deriva de runtime das actions v4.

### Sanitizers — DÍVIDA CI ABERTA

O job ASan/UBSan instrumenta corretamente o game code quando é executado, mas atualmente é condicionado a eventos que não incluem `push` para `main`.

Decisão: não misturar esta alteração com a correção do artifact. Criar uma tranche própria de CI hardening para garantir cobertura de sanitizer no caminho de integração de `main`, sem duplicar custos desnecessários.
