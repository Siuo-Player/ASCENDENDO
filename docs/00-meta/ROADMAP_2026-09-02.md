# ASCENDENDO — Roadmap operacional — 02/09/2026

## Baseline

- `main`: `5f29e3d5f959368b999c4cb54d1438e4a4b111b7`
- Estado: funcional, com editor integrado no motor, pipeline de apresentação/compositor em expansão e CI dividido por finalidade.
- Não há PRs abertos neste momento.
- O marcador histórico de versão `9.3` no README já não descreve sozinho o estado atual; esta roadmap passa a ser a referência operacional para a próxima execução.

## Correções da roadmap anterior

A roadmap anterior tinha três problemas de sincronização:

1. tratava o compositor 16×16, a ponte com `LevelData`, a integração no `RenderSnapshot` e a selecção determinística de assets como trabalho ainda futuro, embora as PRs #198–#219 já estejam integradas;
2. misturava evidência estrutural/determinística com aprovação visual/humana de arte;
3. mantinha o Editor como se fosse a única continuação natural da Fase 9, ignorando que a apresentação visual se tornou um workstream próprio.

A partir daqui, essas áreas ficam explicitamente separadas.

## Princípios de execução

```text
regra/domínio
    ↓
presentation model
    ↓
deterministic structural evidence
    ↓
real-campaign evidence
    ↓
deterministic capture
    ↓
human visual/playtest evidence
    ↓
promotion decision
```

Uma etapa posterior nunca é usada para justificar retroativamente uma etapa anterior. Testes estruturais não são aprovação humana; screenshots determinísticos não são, por si só, prova de qualidade estética; referências CC0 não equivalem a assets já aprovados para o produto.

Todos os caminhos novos devem falhar de forma explícita e previsível quando a entrada é inválida ou a representação não é suportada.

## CI atual

A topologia mantida em `main` é:

- `tests.yml`: Linux normal + ASan/UBSan;
- `windows.yml`: validação Windows;
- `deterministic-capture.yml`: captura gráfica determinística.

Não voltar a criar um workflow smoke paralelo apenas para repetir a existência dos runners. Diagnósticos temporários devem ser identificados como tais e removidos quando deixam de responder a uma pergunta técnica real.

## Fase 9 — Editor de níveis + apresentação — em progresso

### 9.1 Configuração de controlos — CONCLUÍDO

- `GameAction` e `KeyBindings` existem.
- Múltiplas teclas por ação e persistência local estão cobertas.
- `Quit`, `OpenEditor`, navegação de editor e ações de UI têm contrato explícito.

### 9.2 Input de rato e viewport — CONCLUÍDO

- posição do cursor e botões estão representados de forma testável;
- janela → espaço lógico usa o contrato de viewport/letterbox;
- hit-testing do menu foi generalizado de caixas fixas para um conjunto de opções.

### 9.3 Estado EDITOR — CONCLUÍDO TECNICAMENTE; validação visual contínua

- `GameState::EDITOR` existe;
- câmara livre e grelha visual são independentes da física;
- acesso por tecla e menu existe;
- a renderização permanece separada da física/runtime semantics.

### 9.4 Manipulação de entidades — PRÓXIMO BLOCO DO EDITOR

Implementar de forma incremental:

- plataforma: colocar, mover, apagar;
- snap de autoria apenas onde explicitamente definido;
- spawn com regras de segurança da plataforma inicial;
- FLAG com identidade de campanha e regra de nível final;
- seleção/hit-test sem alterar a geometria física até a edição ser confirmada.

Aceitação mínima: editar → visualizar → desfazer/cancelar → reabrir → obter a mesma representação semântica.

### 9.5 Guardar + validar — SEGUINTE

- persistir `.lvl` no formato canónico já existente;
- validação da campanha através de `ai_validator.py`;
- execução assíncrona sem bloquear o editor;
- resultado observável e associado ao nível/campanha exatos;
- rejeitar escrita parcial ou estado de validação ambíguo.

### 9.6 Gestão de campanha — SEGUINTE

- reorder tipo playlist;
- `campaign.txt` como fonte de ordem;
- não mover diretamente ficheiros entre diretórios de validade;
- deixar `reorganize.py` responsável pelo routing físico.

### 9.7 Apresentação semântica de plataformas — FUNDAÇÃO CONCLUÍDA

As PRs #198–#219 estabeleceram:

- compositor semântico 16×16;
- máscara de vizinhos com 8 direções;
- preservação de origens contínuas no mundo;
- contactos entre regiões sem snapping global;
- ponte `LevelData → apresentação`;
- execução sobre níveis reais de campanha;
- ligação `RenderSnapshot → WorldRenderer`;
- seleção determinística de candidato de asset;
- request canónico célula → asset;
- validação fail-closed de pedidos inválidos.

O sistema continua deliberadamente **presentation-only**: não altera física, colisão ou geometria de gameplay.

### 9.8 Assets aprovados + integração real — BLOQUEADO POR EVIDÊNCIA, NÃO POR CÓDIGO

A investigação já reuniu candidatos CC0 e respetiva proveniência. O pipeline, porém, não deve transformar automaticamente um candidato investigado em arte final.

Antes de promover qualquer asset:

```text
source
→ licence verification
→ exact file provenance
→ technical compatibility
→ structural candidate eligibility
→ deterministic capture
→ visual/style review
→ explicit approval
→ staged runtime asset
```

O conjunto de props deve permanecer pequeno e coerente. Não importar catálogos inteiros apenas porque são CC0.

### 9.9 Props / ambiente — NOVO WORK PACKAGE

Criar uma camada visual distinta da geometria de plataforma:

- P0 jogador;
- P1 plataforma/landing edge;
- P2 hazard/checkpoint/goal;
- P3 landmarks;
- P4–P6 decoração e ambiente.

Props não podem competir com o jogador ou com a superfície de contacto. A primeira implementação deve privilegiar uma cena pequena, com poucas peças, para avaliar densidade e hierarquia antes de generalizar.

## Fase 9A — Evidência visual

### 9A.1 Captura determinística — CONCLUÍDO COMO INFRAESTRUTURA

Já existe matriz de 16:9, 4:3 e 21:9 em níveis de campanha relevantes.

### 9A.2 Validação humana — PROTOCOLO DEFINIDO; RESULTADO PENDENTE

A evidência humana deve responder a perguntas diferentes das capturas automáticas:

- legibilidade do jogador/plataforma;
- leitura de profundidade;
- distracção por decoração;
- escala e contraste;
- navegação do editor;
- clareza dos estados e affordances.

Nenhum resultado humano deve ser inventado ou inferido da captura técnica.

## Fase 9B — Conteúdo e autoria

Depois de 9.4–9.6 estarem utilizáveis:

1. editor suficientemente completo para produzir níveis sem editar texto manualmente;
2. pequenas cenas de props aprovados;
3. autoria/variação de plataforma através do compositor;
4. biblioteca de assets com proveniência;
5. apenas depois, generalização para um sistema maior de assets/atlas se houver necessidade real.

O objetivo é evitar construir um grande asset pipeline antes de saber que o jogo o necessita.

## Fase 9C — Audio Design — NOVO WORK PACKAGE

O áudio deve seguir a mesma separação usada para a apresentação:

```text
gameplay event
    ↓
semantic audio event
    ↓
sound identity
    ↓
priority / concurrency / mix
    ↓
spatialisation quando relevante
    ↓
accessibility / volume controls
```

Primeiros eventos candidatos:

- jump charge;
- jump release;
- land;
- death/fail;
- checkpoint/goal;
- menu confirm/cancel;
- editor place/move/delete;
- validation success/failure;
- warnings e estados importantes.

Regras:

- áudio nunca deve codificar a regra de gameplay;
- o motor deve emitir eventos sem acoplar diretamente cada sistema a uma implementação de áudio;
- efeitos repetitivos devem ter limites de concorrência;
- o silêncio também é parte do design;
- fontes/licenças dos sons devem ter provenance tal como os sprites.

## Fase 10 — Release portable — FUTURO

- executável standalone;
- sem terminal;
- paths relativos e armazenamento dentro da pasta do jogo;
- falha graciosa quando Vulkan/requisitos não estão disponíveis;
- README separado para jogadores e developers;
- pacote mínimo em disco/memória.

## Fase futura — Partilha de campanhas/runs

Continua apenas como ideia não aprovada para multiplayer de dados. A arquitetura deve permanecer portável e determinística, mas não criar infraestrutura de servidor antes de existir necessidade concreta.

## Dependências que não devem ser quebradas

- Não alterar física ou colisão para facilitar arte.
- Não usar snapping visual para reescrever geometria de gameplay.
- Não transformar fixtures sintéticas em corpus de produto.
- Não considerar “CC0” equivalente a “aprovado”.
- Não generalizar o compositor ou asset pipeline sem evidência de necessidade.
- Não alterar testes existentes apenas para acomodar uma implementação nova.
- Não introduzir novos workflows redundantes.
- Não tratar uma captura determinística como substituto de playtest humano.

## Relação com a investigação transversal

As lições metodológicas consolidadas no trabalho Ares/RedWar aplicam-se aqui como princípios de engenharia, não como código para ser transplantado:

- contratos explícitos antes de optimizações;
- fontes canónicas únicas para semântica;
- separação entre correctness, benchmark e avaliação humana;
- provenance de dados/assets;
- desenvolvimento vs evidência protegida quando existir otimização baseada em dados;
- fail-closed para entradas inválidas;
- snapshots datados do estado do projeto;
- nenhuma promoção automática baseada num único indicador.

ASCENDENDO continua independente do RedWar e não deve importar a arquitetura da Ares ou mover-se para `Siuo-Engine` por causa destes princípios.
